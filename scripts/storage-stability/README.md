# Storage stability operator

This is opt-in operator source, not an installation or authority to execute it.
`checkpoint.py` imports no sibling code until the reviewed root-private inventory
pins all fifteen actor files, including `bootstrap_backend.py`,
`command_process.py`, `canary_native.py` and both preservation modules. The standalone canary watcher,
supervisor and HDD diagnostic retain separate explicit source/authority pins. It accepts two fixed actions: a stopped checkpoint,
and an explicitly authorized manual failover. It has no shell/SQL/command hook,
automatic failover, provider recovery, credential provisioning, retry, operation
adoption, automatic failure resume, or old-snapshot rollback.

Install reviewed actors in `/usr/local/lib/openlegal-storage-stability` with
root-owned, non-writable ancestors, a root:root `0700` installation directory and
`0600` actor files. Inventory and authority are separate root-private files under
`/etc/openlegal-storage-stability`. They are not generated by this program. The
inventory pins the exact host, managed epoch, seven original dataset GUIDs in one
pool, images/config/PV/PVC identities, backend command binaries, and every physical
source/backup/journal root. The fixed Linux backend must validate its bounded
`linux` section and actual resource state before any host mutation. Inventory
values are metadata and private credential-file references, never inline secrets,
executable commands or caller-supplied SQL.

`qualify` validates source bytes and the input schema only. It explicitly does
**not** qualify live resources or authorize effects:

```sh
/usr/bin/python3 -I -B /usr/local/lib/openlegal-storage-stability/checkpoint.py qualify \
  --inventory /etc/openlegal-storage-stability/inventory.json \
  --inventory-sha256 ACTUAL_REVIEWED_RAW_SHA256
```

An actual checkpoint additionally requires `--authority` and
`--authority-sha256`. It creates a fresh UUID unless a new explicit UUID is
provided. A daily standing authority may have a null operation ID only for the
checkpoint action with `daily_checkpoint_permitted=true`. Manual failover always
requires an exact new UUID and explicit `manual_failover` action authority.

## Checkpoint and evidence boundary

The fixed order is qualify → stop MCP controllers/jobs → actual process/CRI/
cgroup and SQL drain → actual primary/standby PostgreSQL stop → one coordinated
original-seven plus all active-extra dataset snapshot → stopped SSD copies → guarded lookup resume → bounded
export → isolated restore verification → retention of owned backup chains.

The existing shared lock is opened without creation, and its exact device/inode
is checked before and after flock and before effects. Old actors using that same
lock cannot race this operator. Every operation and phase is exclusive; failure
leaves its bytes and partial effects intact. A failed operation cannot be reopened
or relabelled successful. A new operation requires new explicit assessment of any
remaining resources. Desired replicas0 or an absent Pod never substitute for
actual process/container termination and SQL drainage.

Both journal roots must be on different devices, with exact prepared identities.
Each private file is written O_EXCL, fsynced, read back and directory-synced on
**both** media before its in-memory acknowledgement is published. Prior artifact
bytes and directory identities remain checked. A second-media failure is terminal,
not permission to continue on SSD. Journal content is capped at512MiB/4096
artifacts per operation; each artifact is capped at256MiB. Actual child exit and
owned-process closure evidence come from the reviewed Linux backend; a JSON
`completed` file or method return alone is not proof of a real host action.
Final CLI output says `completed_pending_actual_operator_exit`; systemd or the
calling operator must separately retain the actual process exit status.

The six-hour logical operation budget does not reset per phase. All SSD trees
share one one-hour copy budget, and all retention candidates share ten minutes.
Backend subprocess budgets and actual closure remain necessary. Kernel D-state
I/O/fsync can outlive these clocks; no hard physical shutdown or60-minute RTO is
promised. Unknown outcomes remain unknown and block progression.

## Active PostgreSQL topology

The draft inventory keeps `original_datasets` at exactly seven immutable archive
identities and separately requires `active_datasets` (zero through sixteen).
`inventory.all_datasets()` returns detached original-plus-active records. Every
current HDD dataset must share the original pool and have distinct, nonoverlapping
name, GUID and mountpoint pins; every active extra must be explicitly covered.
A checkpoint receipt includes **all** original and active datasets in one snapshot
group. Original datasets, old snapshots, PVs and history are never removed.

The SSD tree and coverage role is `postgres`, independent of whether that copy is
currently primary or standby. PostgreSQL coverage requires both an HDD dataset
and an SSD tree. After a reviewed SSD promotion and HDD peer reseed, a new pinned
inventory must add the actual new HDD dataset and current primary/standby data
references. Both current database copies, WAL and required assets remain backup
and isolated-restore prerequisites. Core schema acceptance alone does not prove
those backend bindings or a restore. Manual failover currently remains a planned,
explicit old-HDD-primary workflow; emergency unsupported topologies refuse.

Initial seed inventories and authorities, and manual prepared configurations,
use schema2 with `media_profile=cache_hdd_corpus_ssd_primary_v1`. This closed
profile keeps `cache_primary` on HDD and `cache_replica` on SSD, and places
`corpus_primary` on SSD with `corpus_replica` on HDD. Corpus reads therefore stay
on SSD; the existing runtime guard stays in the SSD cache replica. Each target
has an explicit typed `media` record. Kernel mount identity, ZFS GUID or SSD
backing, and whole-device WWID checks establish the physical domain. Logical
primary/replica names do not establish it. Manual source mapping requires the
exact old bound-root and marker role; an incompatible older profile refuses.

## Copy and preservation

Every copied source root is pinned to an already open descriptor. Copies create a
new destination only, never overwrite, and never clean up a partial failure.
Regular files must be single-link. Byte SHA-256, destination byte readback,
UID/GID/mode/mtime and bounded xattrs are verified. Every source inode/ctime and
name set is rechecked, including a late tree witness pass. Nested mounts,
special files and hardlinks are unsupported; they are not labelled corruption or
silently flattened. Symlinks are copied only from an exact reviewed relative-path
→ literal-target inventory and are never followed. Symlink xattrs or metadata
which cannot be preserved are unsupported. Isolated restore must separately
validate/rebind every link target before use; a preserved absolute link is not
permission to traverse the original live root.

The explicit source-root `.openlegal-seed-v1.json` is classified as metadata, not
a permanent legal generation. Its bytes are preserved, but the copy does not
accept its old inode/fsid/boot binding for a new root. Initial/reseed processing
must mint a new per-role proof only after complete reference correspondence.
Tree copying claims byte/metadata preservation, not SQL association validity,
legal publication acceptance, all-writer quiescence, or permanent-blob counts.
Those are independent snapshot/retained-row/blob/WAL/index restore gates.

Each operation's qualify receipt establishes a fresh, private provider/accounting
baseline. The inventory's initial provider projection is not reused as a daily
counter pin. Each later hold-bearing receipt must link its before projection to
the preceding verified after projection. Accounting changes require bound raw
schema29 state/lock observations and actual full process/SQL/clean-runtime-guard
closure. Only same-day monotonically charged attempts, pacing/heartbeat stamps,
and bounded current-canary consumption/time may progress; policy, deadlines,
unknown/unlocked ledgers and foreign holds cannot change. UTC day rollover
refuses safely. A changed hash alone is never evidence. Creation/release requires the actual schema29
readback, bound raw private artifacts, and explicit checked generation/ownership.
A clean hold may be installed only after actual writer drainage. Both install
and release use new generations; old operation receipts confer no new ownership.

Every existing or uncertain provider hold is preserved. Lookup may resume while
collectors remain0. A changed hold can be released only if this operation created
it, it is clean, all closure proof exists and explicit authority permits that
release. Collection resume additionally needs its own explicit permission.
Nothing clears abandoned owner evidence, refunds unknown requests, changes a
quarantined historical Job, or treats a failed prior collection as successful.

## Retention and manual failover

Retention touches only UUID directories inside this tool's marked
`storage-stability-chains` backup namespace. It protects every unverified or
partial chain, every chain younger than14 days, and the latest verified checkpoint
and verification. Deletion accepts only the exact full_self_contained_v1 format
with parent_chains=[], raw pinned full-export and closed isolated-restore
receipts. Any unfamiliar/dependent verified chain refuses the entire prune plan
so an unknown ancestor is protected. No incremental-chain feature is implied.
It refuses nested mounts and hardlinks and never runs ZFS
snapshot destruction, deletes a live source/PV, or deletes database/legal history.
Original and tool-created source ZFS snapshots are left intact; this policy does
not bound their long-term CoW space usage. Any source-snapshot pruning needs a
separate reviewed policy and authority.

Manual failover is a separate, explicit command holding the same lock across
fence_old → verify_latest → promote → reseed → strict_resume. The old primary and
all old writers must be physically fenced, latest acknowledged WAL and index
proved, a new managed epoch bound, and a second durable PostgreSQL/blob copy
reseeded before strict service resume. No older snapshot is used to roll back
acknowledged data. Unsupported or missing backend proof refuses the phase.

If the original journal medium is unavailable, a read-only physical-fence report
may still be prepared separately. State-changing recovery requires a replacement
independent durable journal root pinned by a **new** inventory/epoch/authority.
There is no SSD-only journal fallback. If that medium is unavailable, refusal and
remaining stopped are the expected RPO0-safe result. Same-host recovery is not
independent-site disaster recovery or automatic failover.

## Daily schedule and checks

The timer is `19:00:00 UTC`, which is04:00 Korea the following day. Its environment
file contains only the actual inventory and authority hashes. It invokes the
checkpoint action, never manual failover. `Restart=no` prevents retries. PrivateTmp
is intentionally disabled so the exact existing shared lock remains visible.
After a reboot or device/UID/image/config/epoch/source change, requalify the
inventory and authority before expecting a successful run. Source and schema
qualification are not actual checkpoint/restore acceptance.

Run the offline tests using only disposable `/tmp` fixtures:

```sh
sudo -n python3 -I -B -m unittest discover -s scripts/storage-stability/tests -v
```

Install the local PostgreSQL client library (`libpq5`), or set
`OPENLEGAL_TEST_LIBPQ` to a reviewed native library for the libpq environment
regression. That test connects only to an absent socket in its private `/tmp`
fixture. A missing-library skip leaves this check incomplete.

Copy, xattr, link, late-mutation, partial-journal, lock and retention cases use real
files. Positive two-journal tests mock only the independent-device identity
because every test path must remain under `/tmp`; they do not prove dual-media
power-loss durability. Workflow tests inject an explicitly synthetic backend and
prove phase/authority/failure fencing, not K3s/Docker/ZFS/PostgreSQL actions. Real
physical stopping, snapshots, restore, manual failover, fresh source qualification
and timed production evidence remain separate mandatory gates. No readiness claim
may be inferred from these unit tests.

Source file and directory reads use O_NOATIME without a fallback. An unavailable
permission/filesystem capability refuses the copy. Explicit source symlinks are
never followed, but Linux readlink may update a symlink's own access time on a
writable relatime filesystem; sources requiring immutable symlink-atime must be
mounted read-only/noatime by the reviewed backend. No atime restoration writes are
performed. Copied seed metadata accepts only root-owned single-link 0640/0644
markers and never authenticates a new root by itself. Final acceptance rereads
all destination regular bytes and metadata, then rechecks every destination
inode/ctime and path identity. These are stopped-copy point-in-time proofs, not
protection against a writer starting after return.

Promotion seals only a new-epoch intent and proves application writers remain
inhibited. It does not establish a new durability ACK or public readiness. The
actual protected database epoch binding is required after the second copy has
been reseeded and before strict resume; promotion cannot perform a single-copy
commit merely to manufacture that proof.

## Initial setup and emergency recovery boundaries

`initial_driver.py`, `legacy_prepare.py`, `initial_migration.py` and
`initial_blob_seed.py` form a separately pinned initial maintenance path. They
do not belong to the fifteen-file checkpoint graph. The live ROOT parent keeps
the same shared lock, writer descriptors and dual journal while it observes the
actual producer exits. A historical completion file cannot replace that live
context. One original deadline covers the initial operation; a phase cannot
renew it. The driver fences legacy writers, snapshots the original seven
datasets and migrates schema27 through33. The Blob helper creates four new
roots and verifies the complete physical union, including unreferenced retained
generations, before publishing any seed marker. Its first-seed profile refuses
nonempty or unavailable xattrs rather than silently dropping ACL/security data.
The general stopped-tree copier retains its separately documented xattr behavior.

Initial copying individually fsyncs and fully reads back each regular file.
It batches repeated ancestry checks and directory synchronization across at most
64 files or4MiB;250ms is a scheduling check before the next file, not syscall
preemption. A larger validated file runs alone. Every batch synchronizes its
dirty shard directories, target root and prepared parent before returning.
Complete metadata, byte/hash, reference and late-witness scans still precede
the four seed markers and final correspondence proof. Partial batches remain
unpublished and cannot be adopted after failure. This reduces repeated work;
it does not establish a particular speedup or initial-outage duration.

These helpers do not provision roles or TLS, create a PostgreSQL peer, bind the
first strict epoch, publish a pre-ACK epoch certificate, start serving, or resume
collection. Initial pair/controller integration and native qualification are
separate prerequisites. Complete copy timing must fit the original budget before
an outage starts. A small synthetic copy measurement cannot establish that fit.
Logical Blob roles do not authorize a storage-placement change: keeping corpus
reads on SSD requires an explicitly qualified SSD primary and HDD peer throughout
initial seeding, configuration, certification and recovery.

`emergency_backend.py` and `emergency_native.py` currently provide bounded
surviving-standby observations and validation of a previously installed epoch
certificate. They cannot dispatch promotion, reseed a second copy, create their
own pre-fault authority or return Ready. Their source review and harmless process
tests do not establish end-to-end failed-primary recovery. Physical fencing,
replacement journal media, certificate installation before the first public ACK,
promotion/reseed integration and actual native drills remain required.

## Provider observation helper boundary

`provider_backend.py` is an inert, fixed schema29 adapter, imported after the
Linux/restore/manual siblings in the exact fifteen-file source graph. The API is
`observe(backend,op,stage,container=None,baseline=None)`,
`hold(backend,op,before,container=None)`, `release(...)`, and
`phase_facts(backend,op,before,after,closure=None,mutation=None,collectors_resumed=False)`.
All optional arguments are keyword-only. Observations return an opaque port with
`projection`, `wrapper`, `artifact`, `sha256`, query-artifact references, current
checkpoint readback and the exact target container. Callers may inspect it but
may not edit/relabel it: every later helper reloads the original acknowledged
canonical bytes from both journals. Each phase has one exclusive before/after
artifact; no operation or stage is replayed or overwritten.

Qualification takes one actual SQL snapshot after read-only binding checks,
then `observe(...,'after',baseline=before)` explicitly reuses that same snapshot
without claiming a second independent read. A supplementary artifact names the
actual query and both wrappers. The raw query envelope also binds operation,
phase, stage and exact target container. Opaque fields cannot select another
container. Only the original pinned primary is accepted, except explicit manual
strict resume, which requires the byte-verified successful reseed receipt and its
exact promoted primary. Root target/image/mount authentication remains an
additional independent gate. Baseline reuse in any other phase refuses.
Fresh reads call only the protected schema29 observe(uuid) function with the
backend's2s SQL deadline. Its dedicated function owner holds budget/control
SHARE locks and derives one fresh ledger-slot/control/state/owner snapshot.
The named login needs schema USAGE and exact EXECUTE grants; it receives no
direct table/slot function grants or superuser fallback. Server-GUC caps and
actual role/ACL execution are backend/SQL integration gates. The function derives ledger-slot
lock provenance, full hold control, schema29 state and active checkpoint owner;
mutable inventory counts are never substituted.

A foreign or uncertain existing hold is preserved without a new audit mutation.
A new clean hold requires a drained phase and no owners. Release additionally
requires the validated deeply immutable operation authority BEFORE SQL, a
verified same-operation held receipt/intent/generation, unchanged accounting and
actual current readback. Both mutation helpers call only LinuxBackend's
`_sql_mutation`, which owns the original2s pre-effect identity/COMMIT/fresh-WAL
ACK contract, and require its actual `initial/before/after` ACK artifact before
accepting the readback. An exception or missing/mismatched ACK remains unknown;
the helper never resends, clears an owner, refunds usage, provisions a role,
prints a credential, or performs collection startup. Root-owned physical
closure is supplied as raw typed rows and bound to the after-observation hash.
The core validates all candidate facts independently before accepting a phase.
These offline helper tests mock SQL/commands and do not prove an actual database
role grant, WAL flush, command exit, physical closure, or deployment acceptance.

## Initial enrollment components

The initial enrollment modules are separate, callable preparation components;
they are not added to the fifteen-file checkpoint dispatch registry. Their
inventories separately pin the producer source and every preceding raw capability.
A source-owned caller must retain the same live ROOT backend, shared lock,
writer descriptors and original deadline throughout this order:

1. `initial_driver.run`: fence writers, preserve the original data and apply the
   compiled initial migration manifest through its two fixed child phases.
2. `initial_blob_seed.run`: verify the complete retained subset and seed the four
   explicit mixed-media Blob roles, including physical permanent generations
   without current SQL references.
3. `initial_role_prepare.run`: use one fixed role transaction to create nine new
   named roles and assign source-fixed grants and the 28 new function owners.
4. `initial_provider_maintenance.run`: execute the official pinned server's fixed
   plan/apply/readback sequence once, preserving accounting and retained history,
   and reconcile its audit and the actual owned child exit.
5. `initial_pg_pair.run`: qualify the new SSD PostgreSQL target, copy and verify
   the whole cluster, start the named TLS peer and perform the first protected
   binding with `expected_old=NULL`.

These components do not start serving, release collection or establish Ready.
The original initial-enrollment deadline is at most 2400 seconds; an additional
component cannot renew it. Unknown COMMIT, command, SQL or helper ownership keeps
ROOT ownership and the held writers; it does not permit replay, adoption or
cleanup. Physical closure may outlive the logical deadline. Private helper
closure observations cannot turn a late result into an acknowledged effect.

Role preparation preserves pre-existing roles and M1–27 function ownership.
The 28 M28–33 function owner transfers and nine new roles are limited to the
source-fixed manifest. Grants to existing administrative functions name only
the new roles. Runtime EXECUTE grants name only new functions, with USAGE on
the new replication schema. The maintenance CLI uses its
separately qualified non-superuser operator. Its local HBA/ident metadata probe
uses a separate fixed read-only `postgres` observer over the protected native
Unix socket; this is not a provider-apply fallback or a permission grant.
Preprovisioned peer/map authentication and explicitly selected existing local
trust are distinct profiles. Local trust is not identity authentication and is
accepted only with the qualified socket and source-owned isolated helper.

## Shared epoch observations

`epoch_observation.py` owns the single strict-configuration hash implementation
and certificate-free native metadata readers. The hash retains the
`openlegal-strict-config-v1` domain while the closed projection uses schema2 and
an explicit mixed-media topology. SSD survivors are exactly `cache_replica` and
`corpus_primary`; unavailable HDD roles are exactly `cache_primary` and
`corpus_replica`. The logical marker roles are preserved.

The emergency wrapper still requires its immutable pre-fault authority and
compares the fresh shared projection with the expected configuration hash.
Common readers do not mint authority or certificates. M33 position and snapshot
queries are standby-only; selecting a primary is refused before dispatch. Fresh
primary prefix/flush evidence, the actual observation and installer child exits,
current-head installation, restart renewal and admission on every Ready path
remain separate integration requirements. Passing the standalone source tests
or returning an initial pair result does not satisfy those requirements.

`epoch_current.py` reads the actual current HEAD before opening its selected
immutable certificate. A stale expected pin, split heads, changed bytes/inodes
or a missing selected file refuses; there is no historical fallback. The caller
retains its root descriptors and serialization locks and separately qualifies
hardware, provenance and completed installation evidence.

`epoch_primary_fence.py` prepares the fixed read-only primary observer outside
the two-second native window, captures prefix/flush through the held executable,
and archives actual command results afterward under the original operation end.
Its approved authority, complete source graph and critical source pins must
agree. Archived windows remain historical data, with explicit SQL closure and
no public ACK or Ready. Neither reader replaces the pending lifecycle hooks.
